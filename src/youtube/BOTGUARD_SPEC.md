# @zpm/youtube/botguard — BotGuard PO Token Engine Specification

## Overview

A pure-Sig implementation of Google's BotGuard attestation challenge system, enabling
YouTube stream access without any external dependencies (no Deno, no V8, no Python).

YouTube requires Proof-of-Origin (PO) tokens for all stream access since August 2024.
These tokens are generated by a proprietary JavaScript Virtual Machine (BotGuard) that
Google sends to clients. This spec defines how to replicate that process natively in Sig.

## Components

### 1. Challenge Fetcher (`challenge.sig`)

**Purpose:** Fetch the BotGuard challenge data from Google's WAA API.

**Endpoint:** `POST https://jnn-pa.googleapis.com/$rpc/google.internal.waa.v1.Waa/Create`

**Headers:**
```
Content-Type: application/json+protobuf
x-goog-api-key: AIzaSyDyT5W0Jh49F30Pqqtyfdf7pDLFKLJoAnw
x-user-agent: grpc-web-javascript/0.1
```

**Request Body:**
```json
["requestKey"]
```

The `requestKey` for YouTube web player is obtained from the InnerTube API via the
`/youtubei/v1/att/get` endpoint (attestation challenge endpoint).

**Response Fields (after parsing):**
- `interpreterUrl` — URL to fetch the BotGuard VM JavaScript
- `interpreterHash` — Hash of the VM script (for caching)
- `program` — Bytecode program to run in the VM
- `globalName` — Name of the VM global object (e.g., "botguard")
- `clientExperimentsStateBlob` — Experiment flags

**Alternative Source:** The challenge is also embedded in the YouTube watch page HTML
as `ytInitialPlayerResponse.attestation.playerAttestationRenderer.botguardData`.

### 2. JavaScript Engine (`jsvm.sig`)

**Purpose:** Execute the BotGuard VM script and run its bytecode program.

This is the core component. BotGuard is a JavaScript program (~500KB minified) that:
- Implements a custom bytecode interpreter (VM within VM)
- Performs environment fingerprinting checks
- Executes cryptographic operations
- Returns an attestation token

**Architecture: Minimal ES2020 Interpreter**

We implement a subset of JavaScript sufficient to run BotGuard:

#### Required JS Features:
- Variables: `var`, `let`, `const`
- Types: number, string, boolean, null, undefined, object, array, function
- Operators: arithmetic, comparison, logical, bitwise, assignment, ternary
- Control flow: `if/else`, `for`, `while`, `do-while`, `switch`, `try/catch/finally`
- Functions: declarations, expressions, arrow functions, closures, `this` binding
- Objects: property access, computed access, prototype chain, getters/setters
- Arrays: indexing, `push`, `pop`, `splice`, `slice`, `indexOf`, `map`, `forEach`, `filter`, `reduce`, `join`, `reverse`, `sort`, `concat`, `includes`, `find`
- Strings: indexing, `charAt`, `charCodeAt`, `fromCharCode`, `split`, `substring`, `slice`, `indexOf`, `replace`, `trim`, `toLowerCase`, `toUpperCase`, `includes`, `startsWith`, `endsWith`, `repeat`, `padStart`, `padEnd`
- Math: `Math.floor`, `Math.ceil`, `Math.round`, `Math.abs`, `Math.min`, `Math.max`, `Math.random`, `Math.pow`, `Math.log`, `Math.sqrt`
- RegExp: basic regex matching (BotGuard uses regex for string ops)
- JSON: `JSON.parse`, `JSON.stringify`
- Typed Arrays: `Uint8Array`, `Uint16Array`, `Uint32Array`, `Int8Array`, `ArrayBuffer`, `DataView`
- Base64: `atob`, `btoa`
- TextEncoder/TextDecoder: UTF-8 encode/decode
- Crypto: `crypto.getRandomValues` (fill buffer with random bytes)
- Date: `Date.now()`
- setTimeout/setInterval (stub — BotGuard uses for timing checks)
- Promise: basic Promise support (BotGuard uses async callbacks)
- Proxy: basic Proxy support (BotGuard probes for Proxy to detect instrumentation)

#### NOT Required (can be stubbed):
- DOM: `document`, `window.location`, `navigator` → return hardcoded browser-like values
- Network: `fetch`, `XMLHttpRequest` → not called during token generation
- Canvas: `getContext('2d')` → return stub that fingerprints as Chrome
- WebGL: → stub
- Worker, SharedArrayBuffer → not used
- WeakMap/WeakSet → can be implemented as regular Map/Set
- Generators/async-await → desugar to callbacks

#### Environment Stubs (what BotGuard checks):

BotGuard fingerprints the environment. Our stubs must pass these checks:

```
navigator.userAgent       → Chrome/131.0.0.0 (Windows NT 10.0; Win64; x64)
navigator.platform        → Win32
navigator.languages       → ["en-US", "en"]
navigator.hardwareConcurrency → 8
navigator.deviceMemory    → 8
navigator.maxTouchPoints  → 0
screen.width              → 1920
screen.height             → 1080
screen.colorDepth         → 24
window.innerWidth         → 1920
window.innerHeight        → 1080
document.visibilityState  → "visible"
document.hidden           → false
Intl.DateTimeFormat().resolvedOptions().timeZone → "Asia/Jerusalem"
```

#### Implementation Strategy:

The JS engine has 4 phases:
1. **Lexer** — tokenize JS source into tokens
2. **Parser** — build AST from tokens (recursive descent, Pratt precedence)
3. **Compiler** — compile AST to internal bytecode (stack-based VM)
4. **VM** — execute bytecode with value stack, call frames, closures

Memory model:
- Fixed-size value pool (64K values max)
- Fixed-size string intern table (128K strings)
- Reference counting for GC (sufficient for BotGuard's short-lived execution)
- Stack-allocated where possible, module-level statics for large buffers

Target: Execute 500KB of minified JS in < 2 seconds on modern CPU.

### 3. Integrity Token API (`integrity.sig`)

**Purpose:** Exchange BotGuard response for an integrity token.

**Endpoint:** `POST https://jnn-pa.googleapis.com/$rpc/google.internal.waa.v1.Waa/GenerateIT`

**Headers:**
```
Content-Type: application/json+protobuf
x-goog-api-key: AIzaSyDyT5W0Jh49F30Pqqtyfdf7pDLFKLJoAnw
x-user-agent: grpc-web-javascript/0.1
```

**Request Body:**
```json
["requestKey", "botguardResponseToken"]
```

**Response:**
```json
["integrityToken", estimatedTtlSecs, mintRefreshThreshold, "websafeFallbackToken"]
```

- `integrityToken` — base64-encoded token for the minter
- `estimatedTtlSecs` — how long the token is valid (~12-72 hours)
- `mintRefreshThreshold` — when to refresh
- `websafeFallbackToken` — fallback if minting fails

### 4. Token Minter (`minter.sig`)

**Purpose:** Generate PO tokens for individual videos using the integrity token.

After the BotGuard VM executes successfully, it provides a "minter" function via the
`webPoSignalOutput` callback. This function:
1. Takes the integrity token (as bytes)
2. Returns a mint function
3. The mint function takes a content binding (video ID as bytes)
4. Returns a PO token (~110-128 bytes, base64-encoded)

**Token Types:**

| Type | Content Binding | Used For |
|------|----------------|----------|
| Content-bound | Video ID | Player requests (`serviceIntegrityDimensions.poToken`) |
| Session-bound | Visitor Data ID | Stream URLs (`&pot=` parameter) |
| Cold-start | Same as target | Temporary token before real one is ready |

**Minter Lifecycle:**
- One minter per session (valid for hours)
- Each video needs a fresh content-bound token
- Session-bound token can be reused across videos
- Minter must be refreshed when `estimatedTtlSecs` expires

### 5. Token Cache (`pot_cache.sig`)

**Purpose:** Cache and manage PO tokens to minimize API calls.

**Cached items:**
- BotGuard VM script (changes ~weekly, keyed by `interpreterHash`)
- Integrity token (valid hours, keyed by visitor data)
- Session-bound PO token (reused across videos)
- Minter state snapshot (skip VM re-execution on restart)

**Cache file:** `.gotliv/botguard_cache.bin`

**Format:**
```
[4] magic: "BGCA"
[4] version: 1
[8] vm_script_timestamp (unix seconds)
[32] interpreter_hash
[4] vm_script_length
[...] vm_script_bytes (compressed)
[8] integrity_token_timestamp
[4] integrity_token_length
[...] integrity_token_bytes
[4] visitor_data_length
[...] visitor_data
[4] session_pot_length
[...] session_pot_bytes
```

## Flow: Getting a Playable Stream URL

```
1. Check cache for valid integrity token
   └─ HIT: skip to step 6
   └─ MISS: continue

2. Fetch challenge from WAA/Create (or extract from watch page)
   → interpreterUrl, program, globalName

3. Download BotGuard VM script (if not cached)
   → ~500KB minified JavaScript

4. Execute VM script + program in our JS interpreter
   → BotGuard response token + minter function reference

5. Call WAA/GenerateIT with BG response
   → integrity token (cache this)

6. Mint session-bound PO token (visitor data as binding)
   → session_pot (for stream URL &pot= param)

7. Mint content-bound PO token (video ID as binding)
   → video_pot (for player request)

8. Make player request with video_pot
   → streaming data with format URLs

9. Append session_pot to stream URLs
   → playable URLs (no 403)
```

## Resource Budget

| Component | Estimated Size | Memory |
|-----------|---------------|--------|
| JS Lexer | ~2 KB code | 64 KB token buffer |
| JS Parser | ~8 KB code | 256 KB AST nodes |
| JS Compiler | ~6 KB code | 128 KB bytecode |
| JS VM | ~12 KB code | 2 MB value pool + stacks |
| Builtins | ~10 KB code | 64 KB string table |
| BG Script cache | — | 512 KB (VM script) |
| Challenge fetcher | ~2 KB code | 4 KB response buf |
| Integrity API | ~1 KB code | 4 KB response buf |
| Minter | ~3 KB code | 256 B per token |
| **Total** | ~44 KB code | ~3 MB runtime |

Execution time target: < 3 seconds for full flow (challenge + VM + mint).
After caching: < 100ms (just mint with cached minter).

## Security Notes

- The WAA API key (`AIzaSyDyT5W0Jh49F30Pqqtyfdf7pDLFKLJoAnw`) is publicly embedded
  in YouTube's client-side JavaScript. It is not a secret.
- PO tokens are ephemeral and bound to either a session or video ID.
- The BotGuard VM performs fingerprinting — our environment stubs must be consistent
  and plausible (real Chrome on Windows user agent, realistic screen dimensions, etc.)
- Google may update BotGuard's checks. The JS interpreter must be robust enough to
  handle arbitrary JavaScript, not just today's specific code.

## Implementation Priority

1. **Phase 1: Challenge + Integrity (no VM)** — Implement WAA API calls, test with
   manually-obtained BG response tokens (proves the API layer works)

2. **Phase 2: JS Lexer + Parser** — Tokenize and parse JavaScript into AST

3. **Phase 3: JS Compiler + VM** — Execute basic JS (test with simple programs)

4. **Phase 4: Builtins + Environment** — Add all required built-in functions and
   browser stubs (test with BotGuard script)

5. **Phase 5: Full Integration** — Wire challenge→VM→integrity→mint→download pipeline

6. **Phase 6: Cache + Optimization** — Add caching, snapshot support, performance tuning
